2.วัตถุประสงค์และความจำเป็น

แยกตามเคสเพราะเป็น workload คนละแบบ มีความต้องการทางเทคนิคต่างกันโดยสิ้นเชิง

เคส A · Lakehouse

ปัญหาปัจจุบัน: รัน prototype บนเครื่องส่วนตัว (Windows 11, RAM 13.9 GB) ซึ่ง Docker Desktop/WSL2 กินทรัพยากรเกือบหมด เหลือ RAM ว่างเพียง ~1.6 GB ไม่เพียงพอสำหรับไปป์ไลน์ขนาด 1 พันล้านตัวอักษร (เคย Out-of-Memory ระหว่างทำงาน) ไม่สามารถรับผู้ใช้หลายคนพร้อมกันได้ ไม่มีการสำรองข้อมูล และไม่เสถียรพอที่จะเปิดบริการ 24/7

เป้าหมาย: เป็น Data Lakehouse Server ประจำ ประกอบด้วย RustFS (object storage) + Trino/Iceberg (query engine) + Superset (dashboard) + NiFi (ingestion) + Qdrant (vector/RAG) รันต่อเนื่อง 24/7 รองรับนักศึกษา/อาจารย์ query และดูแดชบอร์ดพร้อมกัน

ความสำคัญ: หากไม่อนุมัติ จะไม่สามารถเปิดบริการคลังข้อมูลให้สาขา/คณะใช้งานได้ งานวิจัย analytics และการเตรียมคอร์ปัส CPT ต้องดำเนินบนเครื่องส่วนตัวที่ไม่เสถียนและไม่รองรับผู้ใช้หลายคน

เคส B · CPT

ปัญหาปัจจุบัน: ไม่มีฮาร์ดแวร์ GPU สำหรับการเทรน LLM เครื่องส่วนตัวไม่มี GPU เลย ไม่สามารถทำ Continuous Pretraining บนคอร์ปัสภาษาไทย (ปัจจุบันมี ~1 พันล้านตัวอักษร ≈ 891 ล้าน token) ได้

เป้าหมาย: เป็น Training Server สำหรับ CPT ต่อจาก base LLM ที่มีอยู่ เทรน/ปรับแต่งโมเดลภาษาไทยบนคอร์ปัสที่เตรียมไว้ เป็นการใช้งานเป็นช่วงๆ ตามรอบการทดลอง (ไม่ใช่ 24/7)

ความสำคัญ: หากไม่อนุมัติ จะไม่สามารถสร้างโมเดลภาษาไทยที่ผ่านการ pretrain ต่อเนื่องได้ ซึ่งเป็นเป้าหมายหลักของโครงการ และเป็น output ที่จะนำไปตีพิมพ์/ใช้งานในงานวิจัย

3.คุณสมบัติทางเทคนิคที่ต้องการ

เคส A (Lakehouse) = ระบบประจำรองรับผู้ใช้หลายคน · เคส B (CPT) = เครื่องเทรน GPU ระดับงานวิจัย

3.1 ตารางเปรียบเทียบสเปก

รายการเคส A · Lakehouseเคส B · CPT (Training)
ประเภทระบบ On-Premise (หรือ Cloud bare-metal) Cloud GPU instance (หรือ On-Prem ถ้ามี GPU)
ระบบปฏิบัติการ Ubuntu 24.04 LTS Ubuntu 24.04 LTS
CPU 8–16 cores 8–16 cores (สำหรับ data prep/tokenize)
RAM 32 GB (stack ใช้จริง ~3.5 GB resident + Trino heap 4 GB + พื้นที่ buffer) 64–128 GB (ขึ้นกับขนาด model — 7B ต้อง ≥64 GB)
Storage 1 TB SSD (ขยายได้; corpus+catalog+vectors) 500 GB – 1 TB SSD (corpus + weight + checkpoint)
GPU ไม่ต้องการ 1× A100 80 GB (full CPT 7B)
หรือ 1× RTX 4090 24 GB (LoRA/QLoRA 1–3B)
Network 1 Gbps 1 Gbps (ดาวน์โหลด corpus/weight)
ความปลอดภัย เปิดเฉพาะ reverse proxy :443 + SSH; ทุก service หลัง firewall; TLS ผ่าน Let's Encrypt จำกัดเฉพาะ SSH + Jupyter; ไม่เปิดสู่สาธารณะ

3.2 ที่มาของตัวเลข (จากการวัดจริงของ prototype)

  • Lakehouse — RAM: วัดการกิน RAM จริงของ container ทั้ง stack ขณะรัน = ~3.5 GiB resident, ฝ่า heap ceiling ~8–10 GiB (Trino -Xmx2G + query memory 2 GB/node, NiFi JVM ~1.3 GiB). 32 GB คือจุดสมดุลที่รันได้สบาย + มี buffer กัน OOM
  • Lakehouse — Disk: คอร์ปัส 1 พันล้านตัวอักษร = parquet zstd 475 MB; catalog Postgres 77 MB; vectors Qdrant 201 MB → 1 TB รองรับการเติบโต 1–2 ปี
  • CPT — GPU: โมเดล 7B fp16 = weight ~14 GB; full fine-tune ต้องการ ~4× รวม optimizer state ≈ 56 GB → ต้อง A100 80 GB; LoRA/QLoRA ลดเหลือ ~24 GB → พอกับ RTX 4090
  • CPT — token: corpus 1B ตัวอักษร = 891 ล้าน token (วัดจริงด้วย tokenizer แบบทั่วไป) หรือ ~400 ล้าน token (ถ้าใช้ tokenizer เฉพาะไทย) — ปริมาณเพียงพอสำหรับ CPT ระดับทดลอง

4.การประมาณการใช้งานและการเติบโต

รายการเคส A · Lakehouseเคส B · CPT
ผู้ใช้เฉลี่ย 5–15 คน/วัน (นักศึกษา + อาจารย์ query ผ่าน Superset/Trino) 1–2 คน (นักวิจัยที่เทรน)
ช่วงพีค 3–5 concurrent (ช่วงเรียน/ส่งงาน) 1 job รันต่อเนื่อง (multi-day training run)
การเติบโตข้อมูล ~50% ต่อปี (เพิ่ม corpus + ตาราง Iceberg + vectors) → 1 TB รองรับ 1–2 ปี แล้วขยาย ขยาย corpus เป็น 5–10 พันล้านตัวอักษร; โมเดลใหญ่ขึ้น → GPU เพิ่มตามรอบ
รูปแบบการใช้งาน ต่อเนื่อง 24/7 เป็นช่วง 1–4 สัปดาห์/รอบทดลอง (ไม่ต้อง 24/7 ตลอดปี)

5.ระยะเวลาและงบประมาณ

เคส A · Lakehouse

ระยะเวลา: ถาวร — เปิดบริการตลอดโครงการและหลังโครงการสำเร็จ

งบ On-Prem (แนะนำ): เครื่อง ~50,000 บาท (32 GB RAM / 16 core / 1 TB SSD) จ่ายครั้งเดียว + ค่าไฟ/อินเทอร์เน็ตรายเดือน

งบ Cloud ทดแทน: ~$150/เดือน (~5,000 บาท/เดือน)

เคส B · CPT

ระยะเวลา: ช่วงเทรน 1–4 สัปดาห์ต่อรอบ ทดลอง ไม่ต้องรัน 24/7 ตลอดปี

งบ GPU cloud (1× A100 80 GB): ~$1.5–2/hr → 1 สัปดาห์ ~$250–340 (~8,000–12,000 บาท/รอบ)

ทางเลือกประหยัด (1× RTX 4090): ~$0.4/hr → 1 สัปดาห์ ~$70 (~2,300 บาท/รอบ) สำหรับ LoRA

ข้อเสนอแนะ

แยกเครื่อง: แนะนำให้ Lakehouse และ CPT เป็นคนละเครื่อง — Lakehouse ราคาถูกและต้องรัน 24/7 (On-Prem คุ้มกว่า), CPT แพงแต่ใช้เป็นช่วงๆ (เช่า GPU cloud ตามรอบคุ้มกว่าซื้อ GPU ไว้รอ)

ลำดับความสำคัญ: หากต้องเลือกอนุมัติอย่างเดียวก่อน — ขอเคส A (Lakehouse) ก่อน เพราะเป็นฐานระบบที่รองรับผู้ใช้หลายคน ส่วน CPT สามารถเช่า GPU cloud ทดแทนได้ในภายหลัง

การย้ายจาก prototype: prototype ปัจจุบันรันบน Windows + Docker Desktop ไม่เหมาะสำหรับ production — เมื่อได้เซิร์ฟเวอร์ Linux แล้วย้ายด้วย compose.yaml เดิมได้ทันที (มี healthcheck + restart policy พร้อมแล้ว)

หมายเหตุ: ตัวเลขทรัพยากรประมาณจากการวัดจริงของ prototype บนเครื่องส่วนตัว (RAM/CPU/Disk usage, per-container memory, corpus size, token count) เมื่อ ส.ค. 2026 พร้อมสเปก stack: Postgres, RustFS, Trino, Superset, NiFi, Polaris, Qdrant, Redis, OPA. ส่วนที่กรอก [ในวงเล็บ] ให้ผู้ขอระบุเองก่อนส่งเอกสาร
